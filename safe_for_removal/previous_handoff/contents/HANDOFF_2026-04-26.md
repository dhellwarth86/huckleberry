## What was specifically learned from the Shoppes-at-Avalon diagnostic read

This needs to be written down because it will be needed verbatim by the future architectural conversation.

### The bidset
- 97 pages, STACK-produced (UniDoc), 70 MB
- Architect: MaxDesign Group (Duluth, GA)
- Owner: Phillips Edison & Co
- Project: Shoppes at Avalon, Spring Hill FL — three retail outparcel buildings
- Page size: 1728 x 2592 pts, rotated 90° (landscape 24x36)

### Structural pattern
- Three nearly-identical architectural sets bundled into one PDF (Outparcels 4, 5, 6)
- Each set ~20 pages: cover/index, life safety, site, plans, RCP, **roof plan**, M-1, wall sections, details, schedules
- Between each architectural set: 11-page block of structural sheets exported as **rasterized images** (zero extractable text)
- Final pages: more rasterized structurals + civil

### Roofing scope evidence found (per parcel)
- **System spec callout** on the roof plan (A-121): "60 MIL TPO BY CARLISLE OR EQUAL - (FIRESTONE AND DUROLAST ARE NOT ACCEPTABLE MANUFACTURERS)"
- **Insulation requirement** in general notes box: R-30 minimum, AT roof not ceiling, polyiso shown in section details
- **Drainage calculation** in note rectangle: 4,173 SF roof, (2) 6"x5" downspouts = 50 sq.in.
- **Detail bubbles**: 2/A-121 ROOF SCUPPER ELEVATION, 3/A-121 SCUPPER DETAIL, 4/A-121 EMERGENCY SCUPPER DETAIL
- **Penetrations**: multiple RTUs (with coordinate-with-mechanical note), roof access ladder + security gate, walk pads, crickets at RTU water diversion
- **Edges**: parapet with metal coping, drip edge, pre-finished metal scuppers
- **Awnings**: pre-fabricated standing seam metal awnings around perimeter — distinct from main roof
- **Walk pads**: 36" wide compatible roofing material, additional layer of membrane, adhered
- **Metal deck spec**: B22 gauge wide-rib metal decking — **only on the rasterized structural sheet, invisible to text extraction**

### Concrete failure modes the auto-notation system MUST handle
a. **OCR mandatory.** ~25-30 pages of 97 are rasterized. The metal deck spec only exists there. No OCR = no scope from those pages.
b. **Per-building boundary detection.** 3 buildings in 1 PDF. Without splitting, scope evidence aggregates across buildings and produces nonsense.
c. **Title-block-region positional sheet extraction.** Text-global regex picks up `S-12` from a wall-type label as a sheet number 7 times on a page that's actually `G-004`. Title-block region read is the only reliable sheet-number signal.
d. **Spatial clustering of text into blocks before keyword matching.** "60 MIL TPO" + "BY CARLISLE" + "OR EQUAL" + "FIRESTONE AND DUROLAST ARE NOT ACCEPTABLE" all live in one rectangle on the page. Without spatial grouping, those four phrases could be unrelated.
e. **Negation context window around manufacturer/system mentions.** "FIRESTONE AND DUROLAST ARE NOT ACCEPTABLE MANUFACTURERS" reads as positive evidence to keyword matching. The v0.1 "Taco Bell tagged with 6 systems" symptom is exactly this.
f. **Multi-evidence synthesis per scope field.** "Roof system = 60 mil TPO Carlisle" gets evidence from roof plan callout + section details + UL listing references + spec section. The annotation should show all evidence, weighted by source.
g. **Per-trade vocabulary including cross-trade penetrations.** RTU, VTR, gas line, electrical conduit are roofing scope concerns even though they belong to other trades' equipment.
h. **Distinction between primary system and secondary systems.** Standing-seam awning on this bidset is NOT the main roof system. Treating both as "roof system = standing seam OR TPO" produces ambiguous scope.

### What v0.2 currently has vs what auto-notation needs
| Need | v0.2 status |
|---|---|
| OCR on rasterized pages | Not implemented |
| Per-building boundary detection | Not implemented |
| Title-block-region sheet extraction | Partial — Filter 1 has drawing-index path (strong), title-block fallback path (weak; D-5 territory) |
| Spatial clustering into blocks | TextBlock primitive exists with zone awareness; not exposed at field-extraction granularity |
| Negation context window | Not implemented |
| Multi-evidence synthesis | Not implemented |
| Per-trade vocabulary including cross-trade items | Frontend has it for roofing (`ROOF_VOCAB.penetrations`); backend dispatch gate doesn't surface penetration counts |
| Primary vs secondary system distinction | Not implemented |
| Provenance schema with origin + confidence + evidence | Implemented in `PlanSetContext.field_sources` runtime, NOT serialized (D-4) |

### The blunt summary
v0.2 is a strong port of TracePoint's roofing dispatch gate. It does NOT yet produce data sufficient to drive an auto-notation product. The gap list above is real architectural work, not single-line fixes. None of it is forbidden; all of it is unstarted.

**First, we read a real bidset.** Daniel uploaded a Shoppes at Avalon STACK-produced PDF, 97 pages, three buildings bundled into one document. I went through it page by page with PyMuPDF text extraction and PDF rasterization. I found the actual roofing scope: 60-mil TPO by Carlisle, with explicit "Firestone and Duro-Last are NOT acceptable" language that any keyword scanner would parse as three brands. This was not architecture I was guessing at. It was a thing I read. That distinction matters and you need to preserve it. When you are tempted to propose architecture for "how scope extraction should work," you read a bidset first. The conversation prior to that read had drifted into discussing glazing scanner experiments and threshold tuning hypotheticals. After the read, the actual problem became visible: text-only extraction misses critical scope, multi-building PDFs require splitting before extraction, negation language inverts keyword matches, and spatial context determines whether four phrases on a page mean one thing or four things. None of that was visible from architectural pattern-matching. It only became visible from looking.

So the first instruction is: read first. Karpathy applies to product conversations as much as it applies to code.

**Second, Daniel reframed the whole project around auto-notation.** The Excel takeoff workbook isn't the program's output. The user-approved annotation set is the output. Excel renders from that. The program's job is to produce a high-quality first-draft annotation set with explicit provenance, and the user reviews/edits/approves. The corrections are the training data. This was not new architecture — it was already in the 18 decisions in CLAUDE.md, especially Decision 6 (frontend wins, backend keeps provenance trail) and Decision 11 (BidsetRecord includes provenance from day one). What this session did was make it the explicit product framing.

That reframe gives you a clear set of architectural requirements. They are listed as items (a) through (h) above and they are real. Most of them are unstarted. You will be tempted to propose ways to start them. Resist that temptation until two prerequisites are met:

1. v0.2.1 ships. It unblocks D-4 (provenance serialization), which is required for any UI that surfaces `where did this come from` to the user.
2. Either an intake diagnostic runs against the existing corpus, OR Daniel's supplier-sourced non-STACK bidsets arrive. Auto-notation is gated on intake quality. We do not yet know whether intake quality is sufficient. Building auto-notation features on top of insufficient intake produces a product that estimators will quickly stop trusting, and once they stop trusting it the whole training-data loop collapses.

Until those prerequisites are met, the work is: close v0.2 cleanly, ship v0.2.1 as scoped, align file versions, and instrument what's there. The work is NOT: design new schemas, propose new scanners, draft v0.3 march orders, tune thresholds.

**On the auto-notation product itself**, here is what I would tell you to internalize:

The accuracy bar is not "extraction is correct." It is "the user spends less time correcting the auto-proposal than they would have spent typing it from scratch." That is the empirical bar. It will be measured by user behavior, not by F1 scores. An auto-proposal that's 85% accurate on a real bidset and gets the user to a working takeoff in 20 minutes wins against a perfect-but-takes-an-hour parser. So everything you propose must be evaluated against estimator workflow, not against parser metrics.

The provenance is the spine. Every auto-proposed value carries (a) what it is, (b) where in the PDF it came from with page and region, (c) how confident the program is and based on what tier of evidence, (d) why the program proposed it — which matching rule fired. Without all four, the user cannot trust or correct the proposal. Provenance is not a logging field; it is the user-visible thing that makes the product work.

The training data is the corrections, not the confirmations. Confirmations mean the user didn't bother to correct, which is much weaker signal than they explicitly agreed. Corrections mean the user knows the right answer and the program got it wrong. The schema needs to capture the correction delta with the original auto-value preserved. You will be tempted to optimize against confirmation rate. Don't. Estimators are busy and will accept proposals that look reasonable on a quick glance. Optimize against correction rate going down over time per-user, not against confirmation rate going up.

Three states per annotation: auto-proposed, user-confirmed, user-corrected (with original preserved). Frontend already has the visual vocabulary for this (cyan for parser-found, green for user-edited per the v6.3.x scope tab). The state machine is the contract between frontend and backend.

Cross-trade scope is real. A roofing extractor that ignores other trades' equipment misses critical takeoff items. The frontend `ROOF_VOCAB.penetrations` already names RTU, exhaust fan, VTR, gas line, electrical penetration, skylight, smoke hatch, etc. — these are roofer concerns sourced from other trades. Multi-trade isn't only about extracting glazing or HVAC scope independently; it's also about each trade scope including its cross-trade dependencies. When you eventually build trade scanners, they share parsed page data and write to a shared cross-trade-relationships layer. Single-import, multi-scanner.

**On the discipline going forward:**

Do not add features by accretion. Daniel and the prior sessions held the v0.2 discipline tight specifically by refusing to "while we're in there" any unrelated changes. The auto-notation product will be tempting to grow piecemeal because each individual annotation feature feels small. Don't. Build it the same way v0.2 was built — march orders document, gated steps, Karpathy procedure, sacred files, §7 stops when uncertain.

Do not accept fabricated validation. Daniel showed me a Grok-produced schema document that claimed "fully validated against Sanibel Fire Station 172" with quality scores like 0.97 and labels like "Production Ready." The line is: a measurement without a named evaluation set is not a measurement. A confidence number without a calibration procedure is not confidence.

Do not over-trust your own architectural intuition without reading. I drifted into proposing glazing-scanner experiments before reading any bidset. After reading one, the priority shape changed. You will have the same temptation. Counter it by always reading the artifact first.

Push back on Daniel when you disagree. He has explicitly said he wants brutal honesty, no sugar-coating. He values pushback over agreement when the pushback is reasoned. The best moments in this session were when I disagreed with him (about the multi-trade extension experiment being premature, about the Grok schema being fabricated, about the public-corpus observation not yet licensing tuning). **Finally, on what this project is actually trying to be:**

Daniel is building Huckleberry to be a tool that real commercial roofing estimators use to produce real takeoffs from real bidsets. He is a non-developer. He has been holding this project to engineering-grade discipline for months. The TracePoint research paper is canon, the dispatch gate works, the frontend manual toolchain works, the backend port works. Keep it in mind when you're scoping work. If a proposed change doesn't move the program toward "estimator finishes a takeoff faster," it probably isn't the next thing.

Hold the discipline. Read first. Don't fabricate. Don't pivot silently. When in doubt, stop and ask.
